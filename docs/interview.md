# TeamDesk 面试准备清单

本文围绕前端设计题整理项目介绍、面试流程、参考回答和追问。参考回答需要结合实际开发经历表达，不能把已有配置、未来计划或待验证的效果描述为已完成成果。

## 1. 题目与项目定位

题目要求：使用 Claude Code / Codex，基于 React 实现 SaaS 后台管理系统，完成兼容两个 Agent 的 harness engineering。

| 要求                 | 项目对应实现                                                  |
| -------------------- | ------------------------------------------------------------- |
| 至少两个 CRUD 模块   | 成员管理、工单管理，包含跨模块业务约束                        |
| 公共能力复用         | DataTable、FormDialog、Field、ConfirmDelete                   |
| 快速、高质量迭代     | 项目规则、任务型 Skills、静态检查、分层测试                   |
| 快速前后端协作       | Zod 契约、统一请求层、MSW、接口文档                           |
| 可运行项目与 harness | 启动说明、工具版本约束、Agent 入口、共享 Skills、本地检查流程 |

当前定位是 SaaS 后台场景的前端演示。真实认证、多租户、复杂权限、持久化和生产运维不在当前实现范围内。

回答重点问题时，使用：问题 → 选择 → 实现位置 → 验证方式 → 当前限制。

## 3. 两分钟项目介绍

> TeamDesk 是一个团队工单管理后台，包含成员和工单两个 CRUD 模块。两个模块存在业务关联，例如工单指派成员、关联工单的成员禁止删除，以及停用成员不能被新指派。
> 我主要围绕三个目标设计：通过公共组件复用后台交互，通过接口契约和 HTTP Mock 支持前后端独立开发，通过项目约定、Skills、静态检查和测试支持 AI Agent 持续修改项目。
> 业务上，我重点处理了复杂表单、保存失败保留草稿、历史停用负责人和版本冲突。工程上，一个具体例子是把模块依赖和统一请求入口写成 ESLint 约束，让 Agent 在检查失败后能根据具体位置修正。
> 当前是可运行的前端演示，没有实现真实认证、多租户和持久化，也没有宣称未经测量的效率提升。

## 4. 重点亮点：将架构约定编码为 ESLint 约束

### 4.1 面试表达

> AI 生成代码时，功能完成不代表符合项目架构。例如，工单可能直接导入成员模块内部文件，公共组件可能依赖业务模块，页面也可能绕过统一请求层调用 fetch。
> 我把可以自动判断的约定落实到 ESLint：限制 shared 的依赖方向，限制业务模块依赖应用入口、路由和 Mock，限制跨模块访问内部文件，并检查请求入口。
> 配置扫描 src/features 的直接子目录，为各模块生成边界规则。新增模块后，下次运行 ESLint 会自动纳入检查，减少手工维护模块名单的遗漏。
> Agent 通过 AGENTS.md 了解约定，通过 lint 获得具体违规位置和消息，再修正代码。本地按项目约定运行检查；当前仓库没有配置 CI workflow。

### 4.2 对应代码与价值

实现位置：`eslint.config.js`。

| 实现                 | 作用                           | 边界                         |
| -------------------- | ------------------------------ | ---------------------------- |
| 扫描 features 子目录 | 自动生成模块边界配置           | 假设直接子目录就是业务模块   |
| shared 导入限制      | 避免公共层反向依赖业务和组装层 | 根据导入字符串匹配           |
| 跨模块导入限制       | 引导使用公开入口               | 不等同于完整模块依赖解析     |
| 业务层导入限制       | 防止业务依赖入口、路由或 Mock  | 新路径约定需同步检查         |
| fetch 调用限制       | 引导统一错误处理和响应校验     | 只覆盖配置中的调用语法       |
| lint 与本地检查      | 为违规提供可重复反馈           | 不能自动判断所有业务设计问题 |

### 4.3 典型追问

**问：有 AGENTS.md，为什么还需要 ESLint？**

> 自然语言负责解释规则，但可能被遗漏。ESLint 对可明确判断的要求提供自动反馈，两者分别承担指导和验证。

**问：规则会不会被绕过？**

> 会。导入规则主要匹配路径字符串，fetch 规则匹配指定 AST 形态，别名调用等写法可能不在覆盖范围内。它用于拦截常见违规，不能当作安全隔离或完整架构证明。

**问：怎么证明规则有效？**

> 用正反例验证：公开入口导入应允许，内部文件导入应拒绝；请求层可用 fetch，页面直接调用应拒绝；新增模块也要验证自动纳入。现有 lint 通过只说明当前代码没有触发规则，不能证明规则覆盖完整。

**问：新增模块后，是否完全不需要维护配置？**

> 模块名单无需手工增加，但目录结构、别名、文件类型或公开入口约定变化时仍需维护规则。

**可用于简历的表述：**

> 将模块分层和统一请求入口约定编码为 ESLint 约束，自动发现业务模块，并结合本地检查为 AI Agent 提供可定位的违规反馈。

## 5. 架构与公共组件问题

### 5.1 为什么选择成员和工单？

> 两个模块既能复用 CRUD 基础能力，又有负责人、停用、关联删除等协作规则，可以在较小规模下展示真实业务问题。

### 5.2 为什么按 app、features、shared、mocks 分层？

> app 负责组装，features 按业务组织，shared 提供业务无关能力，mocks 实现演示服务端。依赖方向明确后，新增需求更容易定位修改范围，也更容易约束 Agent。

### 5.3 为什么选这些库？

> Router 管导航和 URL，Query 管服务端数据，Table 管表格模型，RHF 管表单草稿，Zod 管运行时校验。收益是减少自建逻辑，代价是学习和依赖成本，所以应用层没有继续引入全局实体 store 或通用低代码引擎。

### 5.4 DataTable 为什么不请求数据？

> 接口、缓存和查询参数属于业务层。DataTable 只接收数据、状态和回调，因此可以在不同模块复用，也能独立验证展示和交互行为。

### 5.5 为什么不把表单全部配置化？

> 工单有条件字段、动态数组、异步负责人和状态约束，强行配置化会产生复杂配置语言。我复用字段和弹窗等稳定部分，业务联动采用显式 React 组合。

### 5.6 成员改名后，工单名称如何更新？

> 工单通过成员模块公开入口复用成员查询。成员保存后失效 members 前缀，名称查询随之更新，不在工单里另存一份名称状态。

## 6. 状态管理与复杂表单问题

### 6.1 为什么区分 URL、Query、RHF？

> URL 保存可恢复和分享的列表条件，Query 保存接口数据及缓存，RHF 保存未提交草稿。弹窗开关等局部 UI 状态仍可用 useState，关键是避免同一份数据存在多个同步来源。

### 6.2 Query 和 Mutation 为什么分开放？

> QueryOptions、query key 和 API 请求放在业务模块的 `api.ts`，供页面、路由 loader 和业务组件复用。Mutation 目前放在页面，因为成功后的缓存失效、关闭弹窗和删除后翻页都属于页面流程。二者通过 QueryClient 配合，不要求写在同一文件；当 mutation 配置需要跨页面复用或页面明显变复杂时，再抽到 `mutations.ts` 或 mutation factory。

### 6.3 Query key 为什么包含完整查询？

> 不同查询结果需要不同缓存身份，否则可能错误复用缓存。AbortSignal 传到 HTTP 层可以取消过时请求，但不能用取消替代正确的缓存身份设计。

### 6.4 列表查询有哪些边界处理？

> 筛选变化回第一页，非法 URL 参数恢复默认，删除最后一页最后一项后回退页码。排序分页由服务端或 HTTP Mock 执行，避免只排序当前页却表现成全量排序。

### 6.5 为什么区分实体、表单值、接口输入？

> 实体包含 id、version 等服务端信息，表单值适配控件，接口输入满足提交契约。通过 toTicketForm 和 toTicketInput 显式转换，避免直接提交实体或修改缓存对象。

### 6.6 故障切回普通工单，impact 怎么处理？

> 转换为接口输入时移除 impact，不能仅依靠隐藏控件。服务端也检查条件字段，防止绕过前端约束。

### 6.7 保存失败为什么不能 reset？

> 草稿可能包含用户尚未保存的修改。失败时保留草稿，切换编辑对象时通过 key 重新初始化；后台缓存变化不能直接覆盖正在编辑的内容。

### 6.8 服务端字段错误如何处理？

> 使用统一错误结构，通过白名单回填已知字段，其他错误显示在表单顶部。控件提交期间禁用，需要等提交结束后再聚焦错误字段。

### 6.9 两个人同时编辑怎么办？

> 更新携带原 version，服务端原子检查并递增，过期返回 409。前端保留草稿，不自动替换版本重试，避免覆盖他人修改。当前关闭重开后获取新版本。

**追问：真实后端如何原子处理？**

> 使用带 id 和 version 条件的更新并检查受影响行数，或其他等价原子机制。不能只先读版本再无条件写入。

### 6.10 停用成员为何还能保留为历史负责人？

> 不能新指派与历史展示是不同规则。搜索仅提供启用成员，已有工单允许保留原停用负责人，服务端需比较新旧负责人。

## 7. 接口与 Mock 问题

### 7.1 为什么选择 MSW？

> 它在 HTTP 层拦截，页面仍走真实请求流程，可以验证参数、状态码、错误处理和响应校验。浏览器与 Node 集成测试复用 handlers，接真实后端时保留页面调用方式。

### 7.2 有 TypeScript，为什么还校验响应？

> 编译期类型不能保证运行时接口内容。请求层使用 Zod 校验响应，即使 HTTP 200，契约不符也不会作为正常数据进入页面。

### 7.3 如何接真实后端？

> 先对齐字段、分页排序、错误结构、领域规则、认证和时间语义，再关闭 Mock、配置地址并验证真实接口。Mock 跑通不能替代真实联调。

### 7.4 当前接口边界是什么？

> 数据在页面内存中，刷新重置；时间是无时区本地时间，演示按 Asia/Shanghai 解释；真实认证和后端原子版本检查仍需接入验证。

## 8. Harness engineering 问题

### 8.1 你如何理解 harness engineering？

> 围绕 Agent 建立可重复工作的环境：提供上下文、明确约束、给出任务流程，并通过工具反馈验证修改结果。项目中由规则、Skills、文档、静态检查和测试共同组成；当前没有配置 CI workflow。

### 8.2 AGENTS.md、Skills、本地检查如何分工？

> AGENTS.md 写长期规则，Skills 写特定任务流程，本地检查验证交付结果。例如统一请求入口是规则，新增 CRUD 的步骤是 Skill，是否违规和测试失败由工具检查。当前仓库没有 CI workflow。

### 8.3 如何兼容 Claude Code 和 Codex？

> AGENTS.md 集中维护约定，CLAUDE.md 引用同一内容。Skills 放在 .agents/skills，Claude 通过相对软链接共享，减少两份内容漂移。两个 Agent 的实际执行效果仍需分别验证。

### 8.4 Skills 越多越好吗？

> 不是。Skills 应有明确适用范围和任务价值，过多可能引入重复、冲突和维护成本。项目任务流程应精简，工具参考按需读取。

### 8.5 怎么证明提高了迭代效率？

> 当前可以展示支持迭代的机制。量化效果需要固定任务，记录完成时间、人工干预、检查失败和回归情况。没有实测就不声称提升比例。

### 8.6 如何评估 harness？

> 可以固定一个新增模块任务，检查 Agent 是否同步契约、Mock、文档和测试，是否遵守分层，是否能根据失败反馈修正。评估还需要人工判断需求正确性，不能只看最终检查是否全绿。

### 8.7 AI 写的代码通过所有检查就够了吗？

> 不够。检查覆盖的是已编码要求，还要审查需求理解、业务语义和测试遗漏，尤其避免实现与测试共享同一个错误假设。

## 9. 测试与现场变更问题

### 9.1 测试如何分层？

> 组件测试验证局部行为，HTTP 集成测试验证契约与业务规则，E2E 验证完整用户流程。优先覆盖失败、冲突和业务边界，不重复验证实现细节。

### 9.2 前端和 Mock 共用 schema，会不会一起错？

> 会。共享 schema 减少契约漂移，但不能独立证明需求正确，所以需要具体业务案例、人工审查和真实后端联调。

### 9.3 为什么提供可触发的失败和冲突场景？

> 让异常路径稳定复现，方便测试和演示失败保留草稿、冲突提示以及重新打开读取新版本。这些端点仅属于 Mock。

### 9.4 现在增加项目管理模块，你怎么做？

> 先明确业务和关联，定义契约，再补 Mock 和文档，实现 API、Query、URL 查询状态、页面与表单，复用公共组件，最后补业务测试并运行检查。模块边界会自动生成，但仍需确认新模块符合目录和入口约定。

### 9.5 下一步优先改什么？

> 为验证题目价值，先用真实增量需求评估 harness；为生产上线，先完成认证、服务端权限与租户隔离、持久化、时间契约和真实联调。根据目标选择优先级。

## 10. 演示顺序

1. 介绍成员和工单的业务关系，展示两个模块的列表与 CRUD。

2. 展示重复邮箱、关联删除保护和停用负责人规则。

3. 展示工单条件字段、动态检查项与时间校验。

4. 展示失败保留草稿、版本冲突及关闭重开。

5. 打开 ESLint 配置，说明自动发现模块和架构约束。

6. 展示 AGENTS.md、CLAUDE.md、共享 Skills 与本地检查流程的分工；说明仓库尚无 CI workflow。

7. 展示实际检查记录，并说明未验证范围。
